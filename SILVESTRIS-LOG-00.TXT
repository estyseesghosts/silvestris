❯ what are some of the pitfalls, avoidables and regression traps we should be   
  avoiding along the way?                                                       

● The issues list these one at a time. Across the whole roadmap they fall into a
  few recurring patterns. The ones I'd watch hardest:

  Process

  - Mixing reformatting with behaviour changes. That's how the uncommitted tree
    became hard to review. Format-only commits should stay format-only (git diff
    -w empty), and every other commit should cover one topic.
  - Building on unpinned or unpushed code. sandcat depending on an uncommitted
    checkout is the current example; lotus carrying its own patched copy is the
    other. Fixes made inside a consumer are invisible to everyone else, and
    they're how bespoke behaviour piles up.
  - Starting visual polish before the test harnesses exist. Measured fixes made
    before #18 can't be verified and will be undone by the next change. The same
    goes for doing visual work before pixel snapping (#12), because snapping
    moves every edge by up to a pixel.
  - Extending code that's about to be replaced. Any time spent on TextArea's
    engine before #58 is wasted, and the same is true of ConfirmationSheet
    before #21 and #22.
  - Calling something done because it's "functional". A coverage row should only
    say functional once a gallery sample and tests exist. Aspirational
    documentation is how consumers end up thinking a component exists when it
    doesn't.

  Architecture

  - Building a second system next to an existing one. No second command system
    beside CommandRegistry, no second text engine beside the core, no second
    divider implementation beside Shell, no per-scroll-source scrollbar
    painters. Build one mechanism and give it adapters.
  - Leaking consumer policy into Silvestris. Upstream the generic mechanism
    (drop zones, key isolation, row accessories), not lotus's tiling rules,
    sandcat's session semantics or chaus's Vim grammar. A consumer name or type
    inside Silvestris is a red flag.
  - Forcing consumers onto Silvestris where they're legitimately 
    domain-specific. chaus's Ropey editor, lotus's PICA and debugger views and
    johjoh's packaging logic stay app-owned. Silvestris should offer pieces they
    can reuse (IME and selection handling, tables, splits) rather than demand a
    rewrite.
  - Controls managing their own lifecycle. Each control having its own
    outside-click listener, Escape handling, z-index constant or theme branch
    makes things like "Escape closed the wrong menu" impossible to fix in one
    place.
  - Holding the wrong lifetime. Async results arriving into surfaces that have
    already closed, callbacks that keep the theme they were created with (lotus
    had to fix this in its source-list icons), and "current responder" state
    that outlives its window.

  Fidelity

  - Taking geometry from memory or from 10.7 and later. Square buttons, overlay
    scrollbars and flat materials creep in easily. Every number should cite a
    reference image or measurements.json, and anything estimated goes in
    docs/exceptions.md.
  - Fixing one control by changing shared tokens. The pop-up's cap must not
    change push-button tokens, and slider thumbs must not reuse the button
    bevel.
  - Treating states as follow-ups. Focus ring, disabled, pressed,
    inactive-window and small/mini sizes are part of a control. Inactive windows
    are where things most often look wrong, because the problem only shows up
    once a second window opens.
  - Rendering where 1.0 is the only scale tested. Hairlines blur at 125% and
    150%. Test goldens must include fractional scales.
  - Measuring designed appearances against 10.6. Dark Aqua and Geist are checked
    against their own goldens, never against 10.6 crops.
  - Copying Apple's artwork. Icons and cursors must be original, and the
    reference crops stay out of this public repo; only hashes and rectangles are
    committed.

  Consumer regression traps

  - lotus guest input isolation. Shell shortcuts must never reach the guest, and
    guest keys must never trigger shell commands. This applies to every focus,
    modal, menu and transient-surface change, and lotus's existing isolation
    tests should move into the shared scenario harness.
  - lotus's inspector focus fix (lotus#74). It fixed a freeze; upstreaming it
    must keep the same behaviour.
  - sandcat's composer. Enter submits, Shift+Enter adds a newline,
    Ctrl/Cmd+Enter submits, drafts survive a failed submit, and the transcript
    keeps following the bottom while it streams. Ctrl+1–4 must not fire while
    the composer has focus.
  - Programmatic updates that fire user callbacks. lotus depends on source-list
    and selection sync not echoing back to itself.
  - Persisted state. lotus's desktop.json with schema_version=1, unknown fields
    surviving round-trips, saved window bounds, and divider saves that are
    grouped together and written on close. Window-role and preference-store
    changes can each break these.
  - Version pins. Changing the GPUI revision silently breaks every consumer
    pinned to the old one, and theme or font changes break lotus's packager hash
    checks.

  Behaviour edge cases that recur

  - Closing a window, entity or document while something is still being
    dispatched to it, while a sheet is open, or while a save is in progress.
  - IME composition: an undo or a focus change while text is still being
    composed, Windows Japanese/Chinese input methods, and emoji or surrogate
    pairs.
  - Password fields leaking through copy, accessibility or IME queries.
  - Sorting, reloading or live updates resetting selection or scroll position
    (match rows by id, never by index).
  - Quitting with several dirty documents, async shutdown work (sandcat's
    storage flush), and native workers (lotus) that aren't documents.

  Performance

  - Idle redraw. Caret blink, the pulsing default button, the indeterminate
    progress bar's stripes and gauges must repaint only themselves and stop when
    the window is inactive. lotus has already measured idle-redraw cost
    (lotus#158).
  - Scale. Tables with 100k rows and large text documents need constant
    per-frame cost, and streaming output must not re-lay-out everything above
    it.

  Testing

  - Tests that sleep on wall-clock time, or that depend on element ids generated
    from indices.
  - Native screenshots used as goldens. Window shadows, font smoothing and other
    windows overlapping make them non-deterministic.
  - Overclaiming what the tests prove. Headless scenario tests check GPUI
    dispatch, not real OS input or window-manager behaviour; that's #50's job.

  If I had to pick three: never let a fix live only in a consumer, never land
  visual changes without a golden, and never build a second copy of something
  Silvestris already has. Most of the other traps follow from breaking one of
  those.
